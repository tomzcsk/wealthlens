### 1.1 ตรวจข้อมูลจริงของ Tom แล้ว — ของค้างมีจริง แต่ยังไม่กัด

อ่าน LocalStorage ของจริง (read-only):

```
คีย์ยอดศูนย์ที่ค้าง: 2
  • กสิกรไทย  2027-07 = 0 · ไม่มีรายการเดินบัญชีรองรับ
  • เงินสด    2027-07 = 0 · ไม่มีรายการเดินบัญชีรองรับ
รายการเดินบัญชีทั้งหมด: 32 · ทุกรายการเป็นชนิด backfill
```

ทั้งสองช่องเป็น **คีย์กำพร้าของจริง** (ยอด 0 และไม่มีรายการรองรับ) — คือสิ่งที่ข้อ 1 พูดถึงเป๊ะ

**แต่มันยังไม่ทำให้อะไรผิดบนหน้าจอ** เพราะบังเอิญตกอยู่ที่ **2027-07 ซึ่งอยู่หลังเดือนล่าสุด (2026-07)** หน้าเติบโตตัดอนุกรมที่เดือนปัจจุบัน จึงยังไม่เดินไปถึงคีย์พวกนั้น

> เขียนไว้ให้ชัดเพราะมันต่างกันมาก: **กลไกพังมีจริง · ของค้างมีจริง · ผลยังไม่ปรากฏ**
> ถ้ามีคีย์ศูนย์ไปตกก่อนเดือนแรกจริงของบัญชีเมื่อไร หมุดจะเลื่อนทันที — และไม่มีอะไรจับได้

### เหตุผลที่เคยปล่อยข้อ 1 หมดอายุแล้ว

F44/F45 ตัดสินให้ปล่อยคีย์ยอดศูนย์ไว้ เพราะ *ตอนนั้น* **ไม่มีใครอ่านรายชื่อคีย์** — มีแต่คนอ่านค่า (บวก 0 = ไม่มีผล)

แต่ **F48 อ่านรายชื่อคีย์**: `netWorthHistory.ts` → `firstMonthOf()` เอา `Object.keys(balances)` มาหา "เดือนแรกที่บัญชีนี้มีตัวเลข" คีย์ศูนย์ที่ค้างอยู่จึงทำให้บัญชี **ดูเหมือนเริ่มถูกติดตามก่อนความจริง**

การตัดสินใจเดิมไม่ผิดตอนที่ตัดสิน — มันแค่ถูกแซงโดยฟีเจอร์ใหม่

## 2. ดีไซน์

### กลุ่ม 1 — บัญชี (ข้อ 1 + 2)

**รวม `applyBankDelta` เหลือตัวเดียว** — ลบสำเนาใน `financeStore.ts` ให้ทุกเส้นทางวิ่งผ่านประตูเดียวจริง ๆ (F40 ตั้งใจไว้แบบนั้นแต่ทำไม่สำเร็จ)

**เก็บกวาดคีย์ศูนย์ — แต่ห้ามลบมั่ว**

กฎที่ผิด: *"ยอดเป็น 0 → ลบคีย์"*
เดือนที่มีรายการเดินบัญชีรวมกันได้ศูนย์ (ฝาก ฿1,000 → ถอน ฿1,000) **ต้องเก็บคีย์ศูนย์ไว้** ไม่งั้นพัง invariant ของ F40:

> ทุก (บัญชี, ปี, เดือน) ที่มีรายการ → Σ tx.amount === balance

**กฎที่ถูก:** ลบคีย์ศูนย์ **เฉพาะเมื่อไม่มีรายการเดินบัญชีในช่องนั้น** — ผูกการลบเข้ากับสมุดรายการ ซึ่งเป็นแหล่งความจริงของช่องนั้นอยู่แล้ว

`applyBankDelta` เป็น pure function ที่ไม่รู้จักสมุดรายการ → การเก็บกวาดจึงต้องอยู่ที่ชั้นที่เห็นทั้งคู่: `withLedger` ใน `financeStore.ts` (ประตูเดียวที่ F40 สร้างไว้ให้ทุก mutation วิ่งผ่าน) เพิ่มขั้นตอน `pruneEmptyBalanceKeys(accounts, transactions)` ท้ายสุดของทุก mutation

### กลุ่ม 2 — กฎที่โกหก (ข้อ 3 + 4)

**สีหมวด:** กราฟ 3 ตัวเลิกถือสำเนา ดึงจาก `EXPENSE_CATEGORIES[cat].hex` (canonical)
**กันไม่ให้กลับมา:** เพิ่ม assertion — ไฟล์ใน `src/components/` ห้ามมี hex ที่ตรงกับสีหมวดใด ๆ (ยกเว้น `types/expense-categories.ts` เอง)

**`ROUTES`:** derive จาก `NAV_ITEMS` — `verify-mobile` วิ่งทุก route ในทะเบียนเมนูโดยอัตโนมัติ เพิ่มหน้าใหม่แล้วประตูตรวจให้เอง ไม่ต้องจำ

### กลุ่ม 3 — a11y (ข้อ 5)

focus trap เขียนเองใน `Modal.tsx` (ui primitive) ไม่เพิ่ม dependency:
- Tab / Shift+Tab **วนอยู่ในกรอบ** (sentinel: element แรก ↔ element สุดท้าย)
- ปิดแล้ว **คืนโฟกัสให้ element ที่เปิดมัน** (จำไว้ตอน open)
- ESC ทำงานอยู่แล้ว — ไม่แตะ
- ไม่ยุ่งกับ `aria-hidden` (คอมเมนต์เดิมอธิบายไว้แล้วว่าทำไมถึงจงใจไม่ใส่)

## 4. สิ่งที่ไม่ทำโดยตั้งใจ

- **ไม่แตะ `aria-hidden` ของ Modal** — คอมเมนต์เดิมอธิบายไว้ว่าทำไมถึงจงใจไม่ใส่ (โฟกัสอาจอยู่ใน subtree ตอนปิด → `aria-hidden` บน ancestor ของ element ที่โฟกัสอยู่ = ผิด a11y เอง)
- **ไม่เขียน migration แยกสำหรับข้อมูลเก่า** — คีย์กำพร้า 2 ช่องที่มีอยู่ (§1.1) จะถูกเก็บกวาดเองในการ mutation ครั้งถัดไปที่แตะบัญชีนั้น เพราะ `pruneEmptyBalanceKeys` ทำงานท้ายทุก mutation ที่ผ่าน `withLedger` — ไม่ต้องมีโค้ด migration ที่รันครั้งเดียวแล้วตายไป
  **แต่ต้องยืนยันตอน implement:** หลังแตะบัญชีกสิกรไทย/เงินสดหนึ่งครั้ง คีย์ 2027-07 ต้องหายจริง ถ้าไม่หาย แปลว่าวางจุด prune ผิดที่ — รายงาน อย่าเงียบ
- **ไม่รวม `Modal` เข้า motion layer** — มันเป็น ui primitive ที่มีสิทธิ์แตะ framer ตามกฎ F42 อยู่แล้ว
